# /EX — Expand & Expound

## Invocation
Explicit `EX`, `/EX`, or `/expand-expound` invokes this skill. Do not trigger on ordinary English words. Run G → PE → Perfect → EX → bounded I until verified exhaustive → QA → visual_QA → karma → C. Reuse established skills without recursive invocation. Never claim C if tests or implementation remain incomplete.

## Prime directive
Improve the **existing** super-admin panel in place. Inspect actual route(s), components, navigation, design tokens, data contracts, permission model, screenshots and tests before changing anything. Preserve existing features, content, auditability, and access. Never invent an existing screen or claim visual inspection without evidence. Prefer incremental, reversible changes and feature flags over wholesale redesign.

## Every new component: required procedure
1. Inventory component ID, owner, purpose, role permissions, dependencies, current screenshot, accessible DOM, metrics, baseline tests, and data sources.
2. **Expand**: identify useful actions, states, data visualizations, contextual help, keyboard support, loading/empty/error states, mobile adaptations, export options and safe automation.
3. **Expound**: explain the purpose, fields, provenance, consequences, permissions, help text, terminology, and error recovery in plain language. Disclose estimates and uncertainty.
4. **PE / Perfect**: generate alternatives within existing design language; score by usability, task success, cognitive load, consistency, accessibility, performance, maintainability, security, and user-reported satisfaction. Do not optimize for engagement at the expense of user agency.
5. Implement the smallest high-value improvement with typed interfaces, tests, migration/rollback plan, and release notes.
6. Compare before/after evidence; measure time-to-task, task success, errors, interaction count, accessibility failures, latency, and optional user feedback. Do not infer happiness from clicks or dwell time alone.
7. Iterate with a finite budget and stopping criteria; preserve baseline if evidence does not support the change.

## Super-admin UI standards
- Existing route/view is authoritative. Responsive mobile-first layout, WCAG 2.2 AA, semantic controls, visible focus, keyboard-only flows, reduced motion, high contrast, screen reader labels.
- Apply DigitalMarketingCo.org visual tokens. Holographic, parallax, glass and animated effects are optional progressive enhancements; never reduce readability or responsiveness.
- Provide clear global navigation, breadcrumb/context, search, filters, saved views, undo where possible, bulk operations with confirmation, and transparent status.
- High-risk actions require role-based authorization, server-side policy enforcement, confirmation, tamper-evident audit events, and recovery mechanisms.
- Separate sensitive bioelectric/health data from marketing analytics; no covert collection or unauthorized profiling.
- All tables have sorting, pagination/virtualization, accessible headings, empty/error states, provenance and exports when authorized.
- All analytics must label measurement units, time zone, collection coverage, and freshness. Never fabricate metrics.
- Protect secrets, sanitize untrusted content, validate inputs, prevent prompt injection and XSS, and use least-privilege APIs.

## Integration with tracker.js
Admin panel may display consented performance, application, operational and separately authorized physiological telemetry. Enforce purpose-limited access and subject-level isolation; never expose raw sensitive recordings in ordinary marketing dashboards. Use server-side aggregates where possible.

## Acceptance gates
- Before/after screenshots and component inventory exist.
- No regression in role permissions, data integrity, keyboard flows, responsive layouts, or existing routes.
- Unit, integration, security, accessibility and visual tests pass in two clean cycles; record actual commands/results.
- Performance and usability changes are measured against baseline or marked unverified.
- Changes are reviewed in preview before production; no automatic production deployment.
- Maintain a provenance ledger with diffs, decisions, test evidence, defects, rollbacks and unresolved blockers.
- Report status separately as specified, implemented, tested, verified. Exhaustive and C only when explicit criteria are satisfied.

## Output contract
Produce component-by-component change plan, implementation diff, test evidence, screenshot comparisons, scorecard, accessibility audit, risk register and outstanding blockers. Never silently omit a requirement. When access to the existing panel is unavailable, produce only a proposed plan and mark visual/implementation verification blocked.
